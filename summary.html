ID·인증·권한: 세 질문을 분리

인증(Authentication)

“누구인가?”를 확인한다. Microsoft Entra ID가 클라우드 ID와 인증을 제공한다.

권한 부여(Authorization)

“무엇을 할 수 있는가?”를 결정한다. Azure 리소스 권한은 RBAC 역할과 범위로 제어한다.

SSO

한 번 인증해 여러 앱에 접근한다. 여러 앱마다 암호를 다시 입력하는 부담을 줄인다.

MFA

암호 외에 휴대폰 앱·코드·전화·생체 등 추가 요소를 요구한다.

조건부 액세스

사용자·위치·장치·로그인 위험 신호를 보고 MFA 요구 또는 접근 차단을 결정한다.

Verified ID

조직이 발급하고 사용자가 제시할 수 있는 검증 가능한 디지털 자격 증명.

Entra ID Protection

위험 사용자와 위험 로그인을 탐지하고 위험 기반 정책에 활용.

Entra Domain Services

도메인 컨트롤러를 직접 관리하지 않고 도메인 가입·LDAP·Kerberos·NTLM 제공.

ARM과 반복 배포

Azure Resource Manager(ARM)[1]

Portal·CLI·PowerShell·API에서 온 요청을 받아 Azure 리소스를 만들고 변경·삭제하는 공통 관리 계층이다. 인증, RBAC, 잠금, 태그가 이 계층에서 일관되게 적용된다.

ARM Template

원하는 최종 인프라를 JSON으로 정의하는 선언형[2] IaC[3]다. 실행 순서를 한 줄씩 적는 대신 “최종 모습”을 적는다.

Bicep

ARM Template보다 읽기 쉬운 Azure 전용 선언형 언어다. 배포할 때 ARM 형식으로 변환되며 같은 결과를 반복 배포하기 쉽다.

멱등성[4]

같은 템플릿을 여러 번 배포해도 불필요한 중복 리소스가 계속 생기지 않고 같은 최종 상태로 수렴하는 성질이다.

시험 구분“Azure 배포 및 관리 서비스/관리 계층”은 ARM, “선언적 JSON”은 ARM Template, “브라우저 셸”은 Cloud Shell, “Linux Bash”는 Azure CLI다.

“당신은 누구인가?”를 확인한다. 암호, 휴대폰, 보안 키, 생체 정보 등을 사용할 수 있다.

권한 부여[14]

인증된 사용자가 “무엇을 할 수 있는가?”를 결정한다. Azure 리소스에는 RBAC를 사용한다.

조직이 정한 암호화·패치·암호 정책 등을 만족한다고 Intune이 판정한 장치다. 조건부 액세스에서 로그인 조건으로 사용한다.

암호 없는 인증[16]

Windows Hello, FIDO2 보안 키, Authenticator 앱처럼 재사용 가능한 암호 없이 로그인한다.

External ID

고객·파트너 같은 조직 외부 사용자가 앱에 접근하도록 ID와 가입 흐름을 관리한다.

Quota[19]구독·리전·서비스별 사용 한도. 부족하면 지원 요청으로 증액 신청

Policy를 더 정확히 이해하기

  • 정책 정의: 허용 리전, 허용 VM SKU처럼 검사할 규칙 한 개
  • 정책 할당: 정의한 규칙을 관리 그룹·구독·리소스 그룹·리소스 범위에 적용
  • Initiative[20]: 같은 목표를 가진 여러 정책 정의의 묶음
  • 효과: Audit은 기록, Deny는 생성 차단, Modify는 속성 수정, DeployIfNotExists는 필요한 구성을 추가
  • Resource Policy Contributor: 정책 정의·Initiative·할당을 관리하지만 사용자 역할 할당을 전부 관리하는 Owner는 아님
기존 리소스 주의새 Policy를 할당했다고 기존 비준수 리소스가 자동 삭제되는 것은 아니다. 비준수로 표시하거나, 효과와 수정 작업에 따라 교정한다.

FOOTNOTES · EASY WORDS

어려운 용어 각주

  1. ↑ARM: Azure의 모든 리소스 요청이 통과하는 중앙 관리 창구.
  2. ↑선언형: 작업 순서가 아니라 원하는 최종 결과를 적는 방식.
  3. ↑IaC: 서버와 네트워크 구성을 문서가 아닌 코드로 관리하는 방식.
  4. ↑멱등성: 같은 작업을 반복해도 결과가 달라지거나 중복되지 않는 성질.
  5. ↑가용성 집합: 같은 데이터센터의 VM을 서로 다른 장애·점검 그룹으로 나누는 구성.
  6. ↑리전 쌍: 재해 복구 등을 고려해 관계를 맺은 같은 지리 내 두 Azure 리전.
  7. ↑RTO: 장애 후 서비스를 다시 살리는 데 허용되는 목표 시간.
  8. ↑RPO: 장애 시 잃어도 되는 데이터 시간 범위.
  9. ↑비즈니스 연속성: 재해 중에도 중요한 업무를 유지하거나 빠르게 복구하는 계획.
  10. ↑L4: IP 주소와 TCP/UDP 포트를 기준으로 통신을 처리하는 네트워크 계층.
  11. ↑L7: URL·호스트·HTTP 헤더처럼 웹 요청 내용을 이해하는 애플리케이션 계층.
  12. ↑Peering: 두 독립 네트워크를 사설 경로로 직접 연결하는 것.
  13. ↑인증: 로그인한 사람이 누구인지 확인하는 과정.
  14. ↑권한 부여: 확인된 사용자가 할 수 있는 일을 정하는 과정.
  15. ↑규격 디바이스: 조직이 요구한 보안 설정과 업데이트 기준을 만족한 장치.
  16. ↑암호 없는 인증: 일반 암호 대신 보안 키·생체·앱 등으로 로그인하는 방식.
  17. ↑도메인 컨트롤러: 회사 네트워크의 사용자·컴퓨터 로그인과 정책을 확인하는 서버.
  18. ↑Spot VM: 중단 가능성을 감수하고 남는 클라우드 용량을 싸게 쓰는 VM.
  19. ↑Quota: 한 구독에서 사용할 수 있도록 정해진 서비스 최대 한도.
  20. ↑Initiative: 같은 규정 준수 목표를 가진 여러 Azure Policy의 묶음.
  21. 텔레메트리: 시스템이 자동 전송하는 성능·상태·사용량 측정 데이터.
  22. KQL: Azure Monitor와 Log Analytics의 로그를 검색하는 질의 언어.
  23. SIEM: 여러 시스템의 보안 로그를 한곳에서 분석해 위협을 찾는 체계.
  24. 재수화: Archive 데이터를 다시 온라인 상태로 돌려 읽을 수 있게 만드는 과정.
  25. 데이터 상주: 법률·정책에 따라 데이터를 특정 국가나 지리 안에 보관하는 요구.
